# FORENSIC-X physical acquisition

## Windows forensic workstation requirement

Physical evidence acquisition must run on a dedicated Windows forensic workstation with elevated privileges where required by the storage hardware. The normal web backend should not be granted unrestricted raw-device access.

## libewf / ewfacquire requirement

The physical acquisition worker uses the libewf toolchain, specifically `ewfacquire`, to create a forensic E01 image. The runtime requires a configured executable path or PATH resolution.

Environment configuration:

- `FORENSIC_ACQUISITION_ENGINE=ewfacquire`
- `FORENSIC_ACQUISITION_EXECUTABLE=<path-to-ewfacquire.exe>`
- `FORENSIC_ACQUISITION_STAGING_ROOT=<job-staging-directory>`

If the engine is unavailable, the job fails clearly and no false success is reported.

## One-time master acquisition rule

FORENSIC-X must acquire a physical source once and create a single authoritative master forensic image. Different investigators must use derived working copies rather than re-acquiring the same device.

## Master vs working copy

- Master image: protected, authoritative, stored in the forensic-images bucket, immutable through normal application operations.
- Working copies: derived from the master and used for investigation workflows; they do not trigger a new physical acquisition.

## Evidence handling

The source device is forensic evidence. The acquisition process is read-oriented and does not format, partition, overwrite, or modify the source. Software read-only access is separate from any hardware write-blocker.

## Deployment requirements

- Windows forensic workstation
- libewf / ewfacquire installed
- administrator or elevated privileges when required
- sufficient staging storage
- sufficient MinIO storage for forensic master images
- controlled access to the physical evidence

## Security and controls

- The web layer never executes arbitrary OS commands.
- The acquisition worker resolves device identity internally and only accepts validated device IDs.
- Output paths are generated by the backend and cannot be selected by investigators.
- A protected E01 image is uploaded through the existing EvidenceStorageService and MinIO object store.
- SHA-256 is recalculated over the produced image and stored in PostgreSQL metadata.
